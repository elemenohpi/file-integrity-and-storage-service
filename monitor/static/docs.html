1. The service

A company keeps a library of reference files. People upload files to the service, and the service tells them whether each file is intact or has been modified. The service also stores files and returns them on request.

Two kinds of people use the service.

  • Users upload files, check whether their uploaded files are intact or modified, and request files from the library. They can do nothing else.
  • Employees can do everything a user can do. They also maintain the library: they add files to it, modify them and remove them.

A file that a person uploads belongs to that person. The library belongs to the company, and everyone may read it.

This page describes the system as you received it. It does not change when you change the system.

2. Architecture

The service is not a single program. It is split into nodes, and each node is in charge of one part of the work. Each node runs in its own Docker container. The nodes talk to each other with messages over TCP sockets.

NodeSource filePortResponsibility
Gatewaygateway.cpp9000Receives every request from users and employees, checks who is asking, and passes the request into the system. It handles one request at a time.
Schedulerscheduler.cpp9001Keeps the list of jobs, hands each job to an execution node and remembers its state and its result. It handles one request at a time. One more thread per execution node sends the jobs out.
Storagestorage.cpp9002Holds the library and the uploaded files, and an index that lists every stored file. It starts one thread for each request.
Execution (exec1, exec2, exec3)execnode.cpp9003Runs the script of a job and returns its output. A node runs one job at a time.

The containers

The file compose.yml describes nine containers. All of them are on one network named fisnet, and they reach each other by name (for example storage).

ContainerWhat it is
gateway, scheduler, storage, exec1, exec2, exec3The six nodes of the service. They are built from one image, fis-node. Each has 256 MB of memory and one CPU, and is started again when its program crashes.
clientA place to run the fis client by hand. The folder samples/ is its working folder.
monitorPlays the people who use the service, measures the system and serves this dashboard. Its port 8080 is the only port that is open to your computer.
outsideA computer somewhere on the internet that has nothing to do with the service.

Places where data is kept:

  • /logs: a volume shared by the six nodes and the monitor. Every node writes its log here.
  • /data: a volume of the storage node. It holds the stored files and the index.
  • /work: a 64 MB disk in memory on each execution node, for the files of running jobs.
  • /config/users.txt: the accounts, copied into the image when it is built.

docker compose down -v deletes /logs and /data, so the next run starts empty.

3. How a job travels

Work is done in two steps. First, a person uploads one or more files. Second, the person submits a script that says what to do with files. The script becomes a job, and the person asks for the result later.

  1. Login. fis login sends the name and the password to the gateway. The gateway looks them up in /config/users.txt and replies with a token. The client saves the token in its session file and sends it with every later request.
  2. Upload. fis upload sends the contents of a file to the gateway. The gateway passes them to the storage node, which writes the file into the uploads of that person and adds an entry to its index.
  3. Submit. fis submit sends the text of a script to the gateway. The gateway passes it to the scheduler, together with the name and the role of the person. The scheduler gives the job a number, adds it to its list in the state waiting, and replies with the number.
  4. Dispatch. The scheduler has one dispatch thread for each execution node. A job is given to one node when it is submitted. Once every simulated second the thread looks for a waiting job of its node, sends it to the node and sets the state of the job to running.
  5. Run. The execution node makes the work folder /work/job-<number> and runs the script line by line. For a check it asks the storage node for the uploaded file and for the library file, saves both in the work folder and compares them. For add and modify it asks for the uploaded file and sends it to the storage node as a library file. For remove it asks the storage node to delete the library file. Every line of the script adds one line to the file output.txt in the work folder.
  6. Finish. The execution node reads the output back, keeps a copy in /tmp/results/job-<number>.txt and replies to the scheduler with the output. The scheduler stores the output and sets the state of the job to done.
  7. Result. fis status and fis result go through the gateway to the scheduler, which replies with the state or with the stored output.

4. Messages

The message format and the socket code are in common.h and common.cpp. Every request uses its own TCP connection: the sender connects, sends one message, reads one reply and closes the connection. The function call does all of this.

A message is a header of 512 bytes followed by the payload. Every field of the header is text, padded with zero bytes up to its full size.

FieldSize (bytes)Contents
type16What is asked, or OK / ERROR in a reply
sender32The name of the program that sent the message
token64The login token of the person making the request
name128A file name or a user name
arg64A small extra value, for example a job number
length16The number of payload bytes that follow the header
reserved192Kept for future use

The payload (data) is, for example, the contents of a file, the text of a script or the output of a job. In an ERROR reply it is the reason.

Requests

The area is library or upload. Library files have the owner -.

5. Jobs and scripts

A script is a text file with one command per line. The first word of a line is the command, and the rest of the line is a file name.

CommandWhoMeaning
check <file>everyoneCompare the file that the person uploaded with the library file of the same name
add <file>employeesPut the uploaded file into the library
modify <file>employeesReplace the library file with the uploaded file
remove <file>employeesDelete the file from the library

The output of a job has one line for each command, in the form <file>: <verdict>.

VerdictMeaning
intactThe uploaded file is the same as the library file
modifiedThe uploaded file differs from the library file
not in libraryThe library has no file with this name
not uploadedThe person has not uploaded a file with this name
added, updated, removedAn employee command was carried out
permission deniedThe person is not allowed to use this command
failedThe command could not be carried out

A command works on the files as they are when the job runs, not as they were when the job was submitted. A command that needs the uploaded file looks for it first: when the person has not uploaded the file, the verdict is not uploaded, whether or not the library has it. A line whose first word is not one of the four commands gives the output line unknown command: <word>.

For example, a user who submits the script on the left receives the output on the right.

check plan.txt                   plan.txt: intact
check draft.txt                  draft.txt: not in library
add plan.txt                     plan.txt: permission denied

The states of a job

A job is always in one state: waiting, running or done. The scheduler keeps the jobs, their states and their outputs in its memory.

6. Files and storage

The storage node keeps two kinds of files on its disk.

AreaPath on the storage node
The library/data/library/<file>
The uploads of a person/data/uploads/<person>/<file>

Every stored file has an entry in the index, the file /data/index.txt. An entry is one line with four fields separated by tabs: the area, the owner, the file name and the state.

RequestWhat the storage node does
PUTWrites the file to the disk and adds an entry with the state stored to the end of the index
GETLooks for the entry of the file in the index, then reads the file from the disk and returns it
DELLooks for the entry of the file, sets the state of its entries to deleted and writes the index again. The file itself stays on the disk

The states of a file

An entry of the index is always in one state: stored or deleted.

The storage is slow. Finding a file takes time, and so does reading it from the disk or writing it to the disk. These delays are simulated, so that they are the same on every computer (see Simulated time and the disk).

7. The client

Users and employees reach the service through a command line client named fis. Its source is client.cpp.

CommandWhat it does and what it prints
fis login <user> <password>Logs in and remembers the session. Prints logged in as <user>
fis upload <file>Uploads the file. Prints uploaded <name>
fis submit <script-file>Submits the script as a job. Prints job <number>
fis status <job>Prints the state of the job
fis result <job>Prints the output of a finished job
fis request <file>Prints the contents of the library file

The client exits with status 0 when the request worked. Otherwise it prints a line that starts with error: on the standard error stream and exits with status 1.

The client reads two environment variables: FIS_GATEWAY is the host name of the gateway (gateway when it is not set), and FIS_SESSION is the file in which the session is remembered ($HOME/.fis_session when it is not set).

Trying it by hand

Run the client in the client container, from the handout folder.

docker compose exec client fis login tester tester123
docker compose exec client fis upload report.txt
docker compose exec client fis submit check.txt
docker compose exec client fis status 12
docker compose exec client fis result 12

Here 12 stands for the job number that fis submit printed. The files report.txt, check.txt and add.txt are in samples/. Whatever you do by hand while a sequence is playing is part of the measurements of that run.

9. Source files

The whole system is about 1,300 lines of C++ in src/. The source file of each node starts with a comment that lists the requests it handles.

FileWhat is in it

The ports, the Message structure and the header of a message. listen_on and connect_to open sockets. send_message and recv_message send and receive one message. call sends a request to another node and waits for the reply. make_reply builds a reply. log_event writes a line of the log. split and trim are small text helpers.

scheduler.cppThe Job structure and the list of jobs. handle_submit, handle_status and handle_result answer the three requests. dispatch is the thread that sends jobs to one execution node. main starts the dispatch threads and accepts connections.
storage.cppload_index, save_index and append_to_index read and write the index. find_entry looks for a file in the index. handle_put, handle_get and handle_del answer the three requests. serve is the thread that handles one request.

The Makefile builds the five programs (gateway, scheduler, storage, execnode and fis) into bin/ with g++. The Dockerfile builds the image that every node and the client container use: Debian 12 with g++, make and the OpenSSL library.

11. The simulation

The system runs as a living simulation. The monitor plays the people who use the service. It follows a pre-planned sequence of events, and each event happens at a fixed time in the sequence. For normal activity the monitor uses the service the way a person would: through the fis client. It builds that client from your source files.

  • The monitor starts playing the sequence as soon as the system is up.
  • The library starts empty. At the start of a sequence the employees fill it.
  • After the monitor submits a job, it asks for the status of the job every two simulated seconds until the status is done, and then it asks for the result. A job that is not done ten simulated minutes after it was submitted counts as lost.
  • A sequence is 60 simulated minutes long. With SPEED=10 it takes six real minutes.
  • After the last event, the monitor waits until every job is done or lost, for at most eleven more simulated minutes. Then the run is finished, and the state at the top of the dashboard changes to finished. The dashboard stays open until you stop the system.

You receive two sequences: normal has normal activity only, and hostile has the same kind of activity together with failures and hostile events. A hostile event may do anything that an attacker on the network could do. The container outside stands for any computer on the internet.

Sequence files

The sequences are in monitor/sequences/. A sequence is a text file with one JSON object per line. The first line names the sequence. Every other line is one event: t is its time in simulated seconds, user is the account, and do is what happens (upload, submit or request). A hostile event has do set to hostile and a kind in place of the account. A submit event carries the lines of the script and the output lines that a correct system gives. You may add sequence files of your own to this folder and select them with SEQUENCE. Read the two files you received to see the form of each event.

12. Simulated time and the disk

The files sim.h and sim.cpp hold the simulated clock and the simulated cost of the disk.

FunctionWhat it stands forCost in simulated time
sim_sleep_ms(ms)WaitingThe given number of milliseconds
disk_search_delay(entries)Looking through entries of the index on the disk1 ms for each entry
disk_read_delay(bytes)Reading a file from the disk30 ms, and 2 ms for each KB
disk_write_delay(bytes)Writing a file to the disk40 ms, and 3 ms for each KB

In the code you receive, these functions are called for five pieces of disk work: searching the index, reading a stored file, writing a stored file, rewriting the index, and writing the archived result of a job. The specification says what you may and may not change about them.

Every delay on the dashboard and in the files of a run is in simulated milliseconds. A measured delay also contains the real time that your computer needs, multiplied by the speed, so a very high speed distorts the numbers. Use SPEED=10 for your measurements, and only compare runs that were made at the same speed.

13. The dashboard

The Dashboard tab shows live charts of the running system. A point on a line chart is added every 20 simulated seconds and covers the two simulated minutes before it. The horizontal axis of these charts is the simulated minute, from 0 to 60. Hover over or tap the ? next to a heading or a tile of the dashboard to see what it shows.

Some headings have a Log scale button. On a log scale every step up the vertical axis is ten times the step below it, so that small and large values can be read on the same chart. The button changes only how the chart is drawn, not the numbers.

Because the monitor asks for the status of a job every two simulated seconds, job latency moves in steps of about 2,000 ms.

15. The logs

Every node writes a log to the file /logs/<node>.log and to its standard output, so docker compose logs -f <node> shows it. Each line is a list of key=value pairs. It starts with ts, the real time in milliseconds, and node, the name of the node.

The times in a log (ms, wait_ms, run_ms) are real milliseconds. The monitor multiplies them by the speed, so the dashboard and the files of a run show simulated milliseconds. queue is the number of waiting jobs.

Some charts are built from these lines, so keep the lines that the system already writes. You may add your own.
